Документация сама не публикуется. Каждый понедельник Kurami готовит предложение правок, открывает для него PR и присылает в канал `#updates` карточку «Docs proposal». Сайт меняется только после твоего клика на **Publish**. Если ты ничего не нажал, сайт остаётся прежним, а карточка ждёт.

## Неделя документации

:::steps
- **Hermes** — в понедельник в 06:00 по местному времени запускает аудит. Задание стоит в расписании дважды в UTC, а нужный час выбирает скрипт.
- **Аудит** — собирает список изменений кода с момента последнего выпуска документации и создаёт черновик: отдельную рабочую копию и ветку `docs/weekly-<дата>-<id>`.
- **Агент** — сравнивает изменения с кодом и страницами, правит только черновик, запускает тесты документации и пишет короткое описание на русском и английском.
- **Воркер** — раз в минуту проверяет черновик, оставляет только разрешённые файлы, коммитит, открывает PR и присылает карточку.
- **Ты** — читаешь карточку и PR и выбираешь кнопку.
:::

Одновременно активно одно предложение. Пока прошлое не закрыто, новый черновик не создаётся: аудит сообщает, какое предложение мешает.

## Карточка и кнопки

В карточке «Docs proposal · ДД.ММ» стоит английское описание правок, список затронутых страниц (новая, изменена или удалена) и строка состояния. Кнопки зависят от состояния.

| Кнопка | Что делает |
|---|---|
| **Publish** | сливает PR в `main`, собирает сайт и подменяет рабочий выпуск; карточка показывает короткий хеш сборки |
| **Discuss** | открывает тред к карточке: там ты пишешь, что поправить |
| **Apply remarks** | заменяет Discuss, когда тред открыт: агент читает только твои сообщения из треда, правит ту же ветку, заново запускает проверки и обновляет карточку |
| **Reject** | закрывает PR и отклоняет предложение; ветка остаётся на GitHub |
| **Retry release** | появляется вместо Publish, если PR уже слит, а выкладка сорвалась; повторяет только выкладку |
| **PR #n** | ссылка на PR |

Карточка меняется вместе с состоянием предложения:

| Состояние | Что значит |
|---|---|
| `drafting` | аудит ещё пишет черновик |
| `ready` | PR открыт, ждёт твоего решения |
| `revising` | применяются твои замечания из треда |
| `publishing` | идёт слияние и выкладка, до пары минут |
| `published` | сайт обновлён, прошлый выпуск сохранён для отката |
| `rejected`, `empty` | предложение отклонено или правок не нашлось |
| `failed` | проверки не прошли или не удалась выкладка; причина написана на карточке |

Нажатие на устаревшую карточку Kurami отклоняет с пояснением и не выполняет позже.

## Рабочая версия сервера после публикации

Когда выпуск Docs проходит проверку доступности, воркер пытается продвинуть серверную ветку `main` к точному SHA опубликованной документации. Подтверждение Publish разрешает эту условную синхронизацию только документационных правок, а не выкладку приложения. Воркер берёт ту же блокировку, что и команда выкладки приложения, и повторяет проверки непосредственно перед продвижением ветки.

| Проверка | Если она не прошла |
|---|---|
| Правильный origin репозитория, ветка `main`, отсутствие правок и неотслеживаемых файлов | Рабочая версия остаётся на месте; правки владельца сохраняются |
| Текущий HEAD — предок опубликованного SHA | Опережающая или разошедшаяся ветка остаётся на месте |
| Каждый промежуточный коммит меняет только разрешённые пути предложения | Исполняемый код блокирует синхронизацию, даже если следующий коммит отменил его правку |
| Блокировка выкладки приложения свободна | Синхронизация заблокирована; даже пустая или устаревшая блокировка требует проверки оператором |

Недостающие Git-объекты скачиваются по точному SHA без обновления отслеживаемых веток. Более новый удалённый `main` не меняет цель. Если рабочая версия уже на опубликованном SHA, действие успешно завершается без изменений. Синхронизация не запускает сборку приложения, миграции, перезапуски или выкладку.

При блокировке документация остаётся в состоянии `published`, а карточка явно показывает **Server checkout sync pending/blocked**. В журнале сохраняются целевой SHA, наблюдаемые SHA рабочей версии и причина. Проверки отставания остаются прежними; публикация документации не доказывает выкладку кода приложения. Автоматического повтора заблокированной синхронизации нет: оператор отдельно устраняет записанную причину.

## Что может менять предложение

Предложение правит только читаемые страницы сайта: Markdown-файлы в `src/human-docs/content/pages/`, журнал изменений `changelog.json`, тест текстов `tests/human-docs/verify.ts` и запись о покрытии `docs/human-docs-coverage-audit.md`. Всё остальное — устройство сайта, сборка, код приложения — воркер отбрасывает ещё до коммита, а при публикации ещё раз проверяет, что в PR нет ничего другого. Поэтому самое плохое, что может сделать плохая правка, — появиться в тексте страницы, а ты увидишь её в PR до публикации.

Описание на карточке — справочный текст: оно не выбирает ни файлы, ни команды. Подробности о проверках, выкладке и откате — на странице [Как устроена документация](@docs-system).
