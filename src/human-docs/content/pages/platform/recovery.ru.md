Резервное копирование в Kurami идёт тремя ступенями, и каждая следующая защищает от более тяжёлой потери. Снимок на том же диске спасает от поломки базы. Зашифрованный пакет хранит секреты для сборки сервера заново. Копия на внешнем хранилище переживает потерю самого сервера. Задание запускается в 03:15 UTC в дни месяца 1, 4, 7 …, то есть не реже чем раз в 72 часа, и итог приходит в канал обслуживания.

## Три ступени

| Ступень | Что внутри | Где лежит | Сколько хранится |
|---|---|---|---|
| Снимок | база Run Store (`orchestrator.db`) и, если есть, база Health (`system-health.db`) база Digest (`briefing.db`) и Ideas (`ideas.db`); `orchestrator.yaml`, `projects.yaml`, `Caddyfile` и настройки Digest `briefing.yaml`, `briefing-topics.yaml`; манифест с контрольными суммами; секретов нет | `$KURAMI_HOME/backups/backup-<время UTC>/` | 14 последних |
| Зашифрованный пакет | самый свежий проверенный снимок, три файла секретов (окружение Hermes, GitHub, превью TailorTales) и реестр cron-заданий Hermes | `$KURAMI_HOME/recovery/*.tar.zst.age` | 3 последних |
| Внешняя копия | тот же пакет и файл с контрольной суммой | облачное хранилище S3, папка `recovery/` | 3 последние пары |

Вторая и третья ступени включаются, только когда ты положил в закрытый файл настроек открытый ключ `age` и доступ к хранилищу. Без ключа Kurami делает только снимок. Закрытый ключ хранишь ты сам вне сервера и вне хранилища: пакет, который можно открыть ключом с сервера, не защищал бы ничего.

## Что не копируется

Код живёт в GitHub и в бэкап не входит. Кроме него, вне любой ступени остаются:

- страницы и медиа выпусков Digest в `state/briefing/` (база `briefing.db` с данными выпусков копируется, готовые страницы — нет);
- база предложений документации `proposals.db` и `stocks.env`;
- остальные секреты: окружения Composio, ключ GitHub App для ревью, окружение превью PickFlick, сессия Telegram;
- логи, данные Docker, рабочие копии, сессии Codex и сами превью.

Поэтому после полной потери сервера готовые страницы и медиа выпусков не вернутся, а часть ключей придётся выпустить заново. База Health хранит ожидающие сообщения тревог и серии, так что восстановленный сервер не забывает открытую проблему; старая копия без неё тоже годится, и следующая проверка начнёт состояние Health заново.

## Что ты видишь

После каждого запуска в канал обслуживания приходит сообщение «💾 Kurami backup completed»: имя снимка, результат проверки SQLite, число файлов, сколько снимков осталось и сколько удалено, время создания. Если включена вторая ступень, ниже идут строки о пакете и о загрузке, или строка «Off-site upload: not configured». Если что-то сломалось, задание падает, а локальный снимок остаётся. Кроме того, [проверка здоровья](@health) поднимает критичную проблему, когда последнему бэкапу больше 84 часов. Устройство стадий описано на странице [Как устроены бэкапы](@backup-internals).

## Копии и подтверждения

```diagram
kind: graph
desc: Выбранные базы и настройки образуют проверенный локальный снимок. Снимок и выбранные секреты входят в зашифрованный пакет. Проверенная загрузка в S3 записывает подтверждение. Код приходит отдельно из Git; политики Cloudflare и исключённое временное состояние восстанавливаются отдельно.
node state "Выбранное состояние" "базы и настройки" store at 0,0
node snap "Снимок" "целостность и суммы" store at 1,0
node bundle "Шифрованный пакет" "выбранные секреты" store at 1,1
node s3 "Копия S3" "проверенная загрузка" external at 1,2
node receipt "Подтверждение" "не проверка восстановления" store at 0,2
node git "Git" "код отдельно" external at 0,1
edge state -> snap
edge snap -> bundle
edge bundle -> s3
edge s3 -> receipt
```

Проверенная загрузка пишет `state/recovery-upload.json`; Health может оценить её возраст. Локальный снимок не подтверждает внешнюю копию, а запись загрузки — проверенную расшифровку и полную сборку сервера. Политики Cloudflare, исключённые секреты и временные сессии требуют отдельных шагов восстановления.

## Проверка пакета

Пакет, который нельзя открыть, хуже, чем его отсутствие, поэтому его стоит проверять. Проверку ты запускаешь вручную на чистой машине, не на рабочем сервере.

:::steps
- **Ты** — скачиваешь из хранилища свежий пакет и файл `.sha256`, сверяешь контрольную сумму.
- **Ты** — запускаешь `recovery-bundle.ts verify` с закрытым ключом, который лежит у тебя офлайн.
- **Проверка** — расшифровывает пакет во временный каталог, отвергает опасные пути в архиве, сверяет каждый файл с манифестом и запускает `quick_check` каждой базы в нём, включая `system-health.db`, `briefing.db` и `ideas.db`, если они есть.
- **Проверка** — удаляет расшифрованные файлы и печатает результат.
:::

## Порядок восстановления

Настоящее восстановление — ручная операция, и порядок в ней важен. Сначала ставится среда, потом код, потом секреты и данные, а опросы проектов включаются в самом конце, чтобы не начать работу на половине состояния.

:::steps
- **Ты** — ставишь зависимости: Git, tmux, Node.js, rootless Docker, Cloudflare Tunnel, Hermes.
- **Ты** — клонируешь репозиторий из GitHub в `$KURAMI_HOME/app`, запускаешь `npm ci` и `npm run check`.
- **Ты** — копируешь конфигурацию из `deploy/config`, ставишь systemd-юниты, плагин и навыки Hermes.
- **Ты** — расшифровываешь пакет и возвращаешь секреты с правами `0600`.
- **Ты** — возвращаешь свежий проверенный снимок баз (`orchestrator.db` и, если вошли, `system-health.db`, `briefing.db` и `ideas.db`) при остановленных сервисах и заданиях или выбираешь чистую базу, если историю запусков не жалко.
- **Оператор** — возвращает клоны проектов, собирает Digest и продвигает одобренный владельцем артефакт документации.
- **Оператор** — ставит все сервисы приложений и оба таймера Digest, включая Projects и общий шлюз; проверяет синхронизацию плагина и навыков Hermes до включения Docker, Hermes и сервисов.
- **Ты** — создаёшь cron-задания заново по списку: у них будут новые идентификаторы.
- **Ты** — проверяешь всё и только тогда включаешь опросы проектов.
:::
