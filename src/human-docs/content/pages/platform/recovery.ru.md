Резервное копирование в Kurami идёт тремя ступенями, и каждая следующая защищает от более тяжёлой потери. Снимок на том же диске спасает от поломки базы. Зашифрованный пакет хранит секреты для сборки сервера заново. Копия на внешнем хранилище переживает потерю самого сервера. Задание запускается в 03:15 UTC в каждый третий день месяца, и итог приходит в канал обслуживания.

## Три ступени

| Ступень | Что внутри | Где лежит | Сколько хранится |
|---|---|---|---|
| Снимок | база Run Store (`orchestrator.db`), `orchestrator.yaml`, `projects.yaml`, `Caddyfile`, манифест с контрольными суммами; секретов нет | `$KURAMI_HOME/backups/backup-<время UTC>/` | 14 последних |
| Зашифрованный пакет | самый свежий проверенный снимок, три файла секретов (окружение Hermes, GitHub, превью TailorTales) и реестр cron-заданий Hermes | `$KURAMI_HOME/recovery/*.tar.zst.age` | 3 последних |
| Внешняя копия | тот же пакет и файл с контрольной суммой | облачное хранилище S3, папка `recovery/` | 3 последние пары |

Вторая и третья ступени включаются, только когда ты положил в закрытый файл настроек открытый ключ `age` и доступ к хранилищу. Без ключа Kurami делает только снимок. Закрытый ключ хранишь ты сам вне сервера и вне хранилища: пакет, который можно открыть ключом с сервера, не защищал бы ничего.

## Что не копируется

Код живёт в GitHub и в бэкап не входит. Кроме него, вне любой ступени остаются:

- база Digest `briefing.db` и каталог `state/briefing/`: выпуски, страницы, медиа;
- база предложений документации `proposals.db` и файлы настроек Digest (`briefing.yaml`, `briefing-topics.yaml`, `stocks.env`);
- остальные секреты: окружения Composio, ключ GitHub App для ревью, окружение превью PickFlick, сессия Telegram;
- логи, данные Docker, рабочие копии, сессии Codex и сами превью.

Поэтому после полной потери сервера история выпусков Digest не вернётся, а часть ключей придётся выпустить заново.

## Что ты видишь

После каждого запуска в канал обслуживания приходит сообщение «💾 Kurami backup completed»: имя снимка, результат проверки SQLite, число файлов, сколько снимков осталось и сколько удалено, время создания. Если включена вторая ступень, ниже идут строки о пакете и о загрузке, или строка «Off-site upload: not configured». Если что-то сломалось, задание падает, а локальный снимок остаётся. Кроме того, [проверка здоровья](@health) поднимает критичную проблему, когда последнему бэкапу больше 84 часов. Устройство стадий описано на странице [Как устроены бэкапы](@backup-internals).

## Проверка пакета

Пакет, который нельзя открыть, хуже, чем его отсутствие, поэтому его стоит проверять. Проверку ты запускаешь вручную на чистой машине, не на рабочем сервере.

:::steps
- **Ты** — скачиваешь из хранилища свежий пакет и файл `.sha256`, сверяешь контрольную сумму.
- **Ты** — запускаешь `recovery-bundle.ts verify` с закрытым ключом, который лежит у тебя офлайн.
- **Проверка** — расшифровывает пакет во временный каталог, отвергает опасные пути в архиве, сверяет каждый файл с манифестом и запускает `quick_check` базы.
- **Проверка** — удаляет расшифрованные файлы и печатает результат.
:::

## Порядок восстановления

Настоящее восстановление — ручная операция, и порядок в ней важен. Сначала ставится среда, потом код, потом секреты и данные, а опросчики включаются в самом конце, чтобы не начать работу на половине состояния.

:::steps
- **Ты** — ставишь зависимости: Git, tmux, Node.js, rootless Docker, Cloudflare Tunnel, Hermes.
- **Ты** — клонируешь репозиторий из GitHub в `$KURAMI_HOME/app`, запускаешь `npm ci` и `npm run check`.
- **Ты** — копируешь конфигурацию из `deploy/config`, ставишь systemd-юниты, плагин и навыки Hermes.
- **Ты** — расшифровываешь пакет и возвращаешь секреты с правами `0600`.
- **Ты** — возвращаешь свежий проверенный снимок базы или выбираешь чистую базу, если историю запусков не жалко.
- **Ты** — возвращаешь клоны проектов, включаешь Docker, Hermes и ingress.
- **Ты** — создаёшь cron-задания заново по списку: у них будут новые идентификаторы.
- **Ты** — проверяешь всё и только тогда включаешь опросчики проектов.
:::
