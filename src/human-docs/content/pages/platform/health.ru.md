Каждые несколько минут Kurami проверяет сервер и Project Orchestrator. Результат всегда виден в одной карточке «🩺 Kurami System Health» в канале здоровья. Kurami не шлёт новое сообщение на каждую проверку: он правит эту карточку на месте. Отдельное сообщение в канале тревог приходит, только когда проблема подтвердилась, изменилась, затянулась или исчезла.

::shot{file="shot-health-card.png" size="card" alt="Карточка System Health в Discord: блоки System и Project Orchestrator, список последних проверок" caption="Заголовок и цвет рамки показывают общий итог; внизу — время последнего обновления и выбор одной из последних проверок."}

## Что показывает карточка

Первая строка — итог: «🟢 All monitored checks are healthy» или «🟠 One or more checks need attention». Цвет рамки зелёный, жёлтый или красный, если есть критичная проблема. Ниже два блока.

| Строка | Что значит |
|---|---|
| CPU | нагрузка за 5-секундную выборку, рядом среднее и пик за скользящее окно и load average |
| RAM | сколько памяти занято из общей, в GiB |
| Network | `online`, `degraded` или `offline` по трём внешним HTTPS-проверкам; скорость обновляется отдельным заданием |
| Disk | процент занятого места и свободные GiB |
| Swap, Uptime | использование подкачки и время работы сервера |
| State DB | результат `PRAGMA quick_check` базы Run Store |
| Docker | сколько контейнеров работает и сколько нездоровы |
| Previews, Worktrees | активные превью и занятые рабочие копии из лимита |
| Quarantine | сколько ресурсов на карантине после спорного удаления |
| Backup | возраст последнего бэкапа и его предел |

Когда что-то не в порядке, ниже появляется блок «Issues»: до восьми строк, лишние свёрнуты в «MORE n additional checks». В подвале стоит время последнего обновления по местному времени.

## Сообщения в канале тревог

Kurami шлёт четыре вида сообщений, и каждое означает своё.

| Сообщение | Когда приходит |
|---|---|
| 🚨 Kurami System Health Alert | подтвердилась хотя бы одна критичная проблема |
| ⚠️ Kurami System Health Warning | подтвердились только предупреждения |
| ⏰ Kurami System Health Reminder | набор проблем не менялся 120 минут |
| ✅ Kurami System Recovered | первая же проверка без подтверждённых проблем |

В сообщении есть список активных проверок, «Top consumers at alert time» — самые прожорливые процессы и контейнеры — и те же блоки System и Orchestrator, что на карточке. Проблема считается подтверждённой не сразу: для CPU, RAM и сети нужно несколько проверок подряд, поэтому короткий всплеск виден на карточке, но тебя не будит.

## Пороги

| Проверка | Предупреждение | Критично | Проверок подряд |
|---|---|---|---|
| CPU | от 85 % | от 95 % | 3 / 2 |
| RAM | от 80 % | от 90 % | 3 / 2 |
| Сеть | отвечает 1–2 из 3 проб | не отвечает ни одна | 3 / 2 |
| Диск | от 75 % | от 85 % блокирует допуск новых запусков | 1 |
| Бэкап | — | старше 84 часов или его нет | 1 |
| OOM-killer, SQLite, Docker, превью | — | любое нарушение | 1 |

Пара «3 / 2» — сколько проверок подряд нужно для предупреждения и для критичной проблемы. Пороги и число проверок лежат в `orchestrator.yaml` (секции `server_health` и `limits`), предел возраста бэкапа — в переменной `KURAMI_BACKUP_MAX_AGE_HOURS`. Подробнее — [Конфигурация](@config).

## Последние десять проверок

Под карточкой стоит список «Inspect one of the last 10 runs…». Каждый пункт — одна проверка: время и итог, например `30.09.26 10:30 · attention`, и краткая строка `CPU x% · RAM y% · Disk z%`. Выбери пункт, и Discord покажет только тебе блок «Health snapshot» с полными цифрами той проверки. Это удобно, чтобы понять, когда именно началась проблема. Kurami хранит десять записей и вытесняет старые.

## Как часто проверять

Интервал проверки меняешь ты в `/kurami settings`, раздел **System Health**. Допустимы 5, 10, 12, 15, 20, 30 и 60 минут; встроенное значение по умолчанию — 20. Kurami переписывает расписание задания в Hermes и пишет строку в канал обслуживания. Форма описана на странице [Настройки](@settings).

Если «Updated» в подвале карточки давно не менялось, сама проверка не запускается, а тревоги об этом нет: сообщить о сбое должен тот, кто не работает. Посмотри состояние Hermes; подробности — в разделе [Как работает мониторинг](@health-internals).
