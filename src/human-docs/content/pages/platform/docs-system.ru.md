Документация — это статический сайт, который собирается из Markdown-файлов в репозитории и выкладывается только после проверок и твоего решения. Неделю документации глазами владельца описывает [Как обновляется документация](@docs-process).

:::glance
- Что делает: собирает страницы на русском и английском в HTML, рисует диаграммы и таблицы справочника и отдаёт их с localhost-сервера
- Запускается: сборка — командой `npm run docs:build` или воркером при публикации; предложения — заданием Hermes по понедельникам
- Где работает: `src/human-docs/`, отдельный systemd-сервис `kurami-human-docs` на порту 8799 только для localhost, за Cloudflare Access
- Состояние: `state/human-docs/` — выпуск `release/`, прошлые `rollback-<sha>/` и база предложений `proposals.db`
- Что видно: сайт `docs.shagon1k.win` и карточки предложений в `#updates`
:::

## Страницы и формат

Каждая страница — это два файла, `<slug>.ru.md` и `<slug>.en.md`, в каталоге своего раздела. В шапке файла стоят `title`, `summary`, `section`, `group`, `order` и `next`; меню сайта строится только из них. Структурные поля `section`, `group`, `order` и `next` в двух языках обязаны совпадать, иначе сборка не стартует. Разбор делает собственный парсер в `markdown.ts`: заголовки, списки, таблицы, блоки кода и контейнеры вроде `:::glance`. Сырой HTML он не принимает, неизвестный блок считает ошибкой.

Главная проверка — паритет языков. Сборка сравнивает «скелет» русской и английской версии: число заголовков второго уровня, диаграммы по идентификаторам узлов, скриншоты, сгенерированные таблицы и блоки glance, guarantees и code-map. Кроме того, сборка проверяет ссылки на другие страницы и пути к файлам репозитория в code-map, а тест `tests/human-docs/verify.ts` ищет в тексте личные данные: имена, часовой пояс, идентификаторы Discord и домашние пути.

На телефоне и планшете у статьи с двумя или более разделами есть компактное раскрытие **На странице** под вступлением. Меню раздела называет текущую страницу, а длинный список прокручивается внутри ограниченной области. Размеры скриншотов берутся из PNG при сборке, поэтому отложенная загрузка сохраняет место под картинку. Отсутствующая статья возвращает страницу 404 со ссылкой на главную Docs на запрошенном языке.

## Диаграммы

Картинки рисует собственный набор `diagrams/kit.ts`, у которого три движка: `graph` для архитектуры, потоков и автоматов состояний, `sequence` для обмена сообщениями и `timeline` для суток. Блок ` ```diagram ` в Markdown превращается в SVG при сборке, а не в браузере. Узлы раскладывает сам набор, а автор задаёт позиции `at колонка,строка`, где авто-раскладки мало.

Набор отвергает схему, которая не читается: шире 980 пикселей или без описания `desc`. Это описание уходит в текстовую альтернативу и помогает тем, кто не видит картинку. В тёмной теме цвета диаграммы заменяются ролями темы через `inlineDiagram`, а у каждой картинки есть отдельный SVG `/assets/diagram-<id>.svg`. Тот же набор умеет отдавать сцену для Excalidraw: `npm run docs:excalidraw` пишет файлы в `dist/human-docs-excalidraw/`. Источник истины остаётся в Markdown, правки из Excalidraw назад не попадают.

## Таблицы справочника из кода

Справочные таблицы состояний и баз строятся из миграций, поэтому они не могут разойтись с кодом. Генератор `reference.ts` применяет все миграции к базе SQLite в памяти и читает схему обратно. Списки из `CHECK (колонка IN (…))` становятся допустимыми значениями. Страница вставляет таблицу блоком `::generated{name="orchestrator-states"}`; доступны `orchestrator-tables`, `digest-tables`, а также `orchestrator-states` и `digest-states`.

Описание каждой таблицы пишется руками в `reference-notes.ts`. Новая таблица без описания ломает сборку, и описание таблицы, которой нет в миграциях, тоже.

## Режимы сборки

| Режим | Команда | Что требует | Что записывает | Что меняет |
|---|---|---|---|---|
| Предпросмотр | `npm run docs:build` | ничего | `mode: preview`, журнал пуст | только локальный `dist/`; сервер его не примет |
| Выпуск документации | `npm run docs:build-docs-release` | чистое дерево | `mode: release`, `docsSha` = `HEAD`, `revision: null` | то, что выкладывает воркер |
| Привязка к приложению | `npm run docs:build-release -- <манифест>` | манифест `{status, appSha}` от доверенного контроллера выкладки | `revision` = `appSha`, журнал изменений | добавляет в журнал изменения с прошлого выпуска |

Сервер документации стартует только с `mode: release` и 40-символьным `docsSha`, поэтому предпросмотр нельзя выложить по ошибке. Доверенного контроллера выкладки приложения в репозитории нет, так что сейчас сайт собирается в режиме «выпуск документации»: журнал изменений пуст, а значение `revision` — `null`. Страница журнала отдельно показывает `docsSha` самой документации и объясняет, что история приложения не связана с подтверждённой выкладкой. Версия документации не подтверждает выпуск приложения.

## Журнал изменений

Журнал `changelog.json` — это список русских и английских пояснений по полному SHA коммита плюс базовая точка. Когда сборка привязана к приложению, она берёт диапазон коммитов от базовой точки до проверенной выкладки. Каждый коммит, меняющий что-то для читателя, должен быть описан. Коммит, затронувший только документацию, можно исключить: путь проверяется по узкому списку. Внутреннюю правку исключают с указанной причиной, а пустое слияние пропускается само. Любой неописанный коммит останавливает сборку. Даты в журнале — даты коммитов, а не выкладки.

## Еженедельное предложение

Предложение правок — это состояние в базе `proposals.db` и рабочая копия документации под отдельной веткой. Аудит в понедельник создаёт запись `drafting`, агент правит рабочую копию, а воркер каждую минуту двигает запись по автомату и обновляет карточку. Воркер правит только белый список файлов, он описан в [Как обновляется документация](@docs-process); остальное отбрасывает до коммита и перепроверяет перед слиянием. Все нажатия кнопок проверяются и записываются атомарно: два одновременных клика не выполнятся оба.

```diagram

В остальных состояниях неожиданное исключение в очередном цикле воркера переводит запись в `failed` с причиной.

## Выкладка и откат

Публикация собирает новый выпуск из `main` в одноразовой рабочей копии и подменяет каталог `release/` целиком. Поэтому читатель видит или весь старый сайт, или весь новый.

```diagram
kind: sequence
desc: Ты нажимаешь Publish. Воркер сливает PR с проверкой последнего коммита, собирает выпуск в одноразовой копии, переименовывает release в rollback и ставит новый каталог на его место. Затем он перезапускает сервис и запрашивает две страницы. При сбое возвращает прошлый выпуск.
actor you "Ты" owner
actor worker "Воркер"
actor gh "GitHub" external
actor site "Сервис docs"
msg you -> worker "Publish"
msg worker -> gh "слияние squash"
self worker "сборка --docs-release"
self worker "release → rollback-sha"
msg worker -> site "перезапуск"
msg worker -> site "GET /en/ и /ru/…"
phase "Сбой"
self worker "failed-sha, вернуть rollback" accent
```

Перед слиянием воркер сверяет последний коммит PR с тем, что показан на карточке, и выполняет `gh pr merge --squash --match-head-commit`: если в PR появился новый коммит, слияние отказывает. Потом воркер убеждается, что слитый коммит входит в `origin/main`, строит выпуск, требует от `build.json` `mode: release` и `revision: null`, переименовывает `release/` в `rollback-<прошлый docsSha>`, ставит собранный выпуск на место и перезапускает сервис. Итоговая проверка — до 20 попыток с паузой полсекунды: страницы `/en/` и `/ru/what-is-kurami/` должны ответить 200. При неудаче воркер переименовывает новый выпуск в `failed-<sha>-<время>`, возвращает прежний, перезапускает сервис и переводит предложение в `failed` с кнопкой «Retry release».

::::example Предложение dp_3f9a1c02b7e4 (данные выдуманы)
:::steps

- **Агент** — правит `platform/health.ru.md` и `.en.md`, пишет описание. Через две минуты воркер видит его.
- **Воркер** — оставляет два файла, запускает тесты, коммитит, открывает PR #318 и присылает карточку. Состояние `ready`.
- **Ты** — читаешь PR, нажимаешь Publish. Состояние `publishing`.
- **Воркер** — сливает PR с проверкой последнего коммита, собирает выпуск из `main`, переносит `release/` в `rollback-<старый sha>` и перезапускает сервис.
- **Воркер** — `/en/` и `/ru/what-is-kurami/` отвечают 200. Состояние `published`, карточка показывает короткий хеш сборки.

## Что может пойти не так

| Ситуация | Что делает Kurami | Что делаешь ты |
|---|---|---|
| Страницы разошлись по структуре RU и EN | сборка падает с указанием разницы | выровнять файлы |
| Нет описания новой таблицы в `reference-notes.ts` | сборка падает | добавить описание |
| Предложение затронуло файл вне белого списка | файл отбрасывается до коммита; в PR его нет | ничего |
| После Publish в PR появился новый коммит | слияние отказывает, предложение возвращается в `ready` | проверить PR и нажать Publish снова |
| Выкладка не прошла итоговую проверку | возвращается прошлый выпуск, новый сохраняется как `failed-…`, предложение `failed` | Retry release или Reject |
| Клон аудита не на `main` или с изменениями | задание падает до черновика; агент сообщает ошибку | починить клон |
| Идёт другое предложение | черновик не создаётся; аудит называет блокирующее | решить его кнопкой |

:::guarantees
- Предложение меняет только страницы, журнал, тест текстов и запись покрытия.
- Публикация происходит только по твоему клику на Publish, на карточке с тем же последним коммитом PR.
- Предпросмотр не может попасть на сайт: сервер принимает только сборку выпуска.
- Новый выпуск подменяет старый целиком, и старый остаётся для отката.
- Выкладка документации не выкладывает код приложения.
:::
