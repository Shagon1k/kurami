Бэкап Kurami — это цепочка из трёх стадий в одном shell-скрипте, где каждая стадия проверяет результат предыдущей и при сомнении падает вслух.

:::glance
- Что делает: копирует базу Run Store и конфигурацию, шифрует пакет для сборки сервера заново и кладёт его во внешнее хранилище
- Запускается: заданием Hermes `kurami-state-backup`, `15 3 */3 * *` — в 03:15 UTC в дни месяца 1, 4, 7 и так далее
- Где работает: `kurami-state-backup.sh` и три TypeScript-команды в `src/system/recovery/`, без агента
- Состояние: каталоги `backups/` и `recovery/` и папка `recovery/` в S3; манифест с контрольными суммами у каждого шага
- Что видно: сообщение «💾 Kurami backup completed» в канале обслуживания
:::

## Стадия 1: снимок

Первая стадия копирует то, без чего не поднять Run Store, и делает это без остановки системы. Скрипт открывает живую базу только на чтение, запускает `PRAGMA quick_check` и выполняет `VACUUM INTO` в каталог `backups/backup-<время UTC>/`. Эта команда SQLite создаёт согласованную копию, даже если в базу пишут: обычное копирование файла могло бы поймать половину транзакции. После копирования скрипт проверяет уже копию.

Рядом ложатся `orchestrator.yaml`, `projects.yaml` и `Caddyfile`; ссылки вместо файлов скрипт отвергает. Последним записывается `manifest.json` со всеми файлами, их размерами и SHA-256 и с пометкой `secretsIncluded: false`. Потом скрипт оставляет 14 последних снимков (значение `KURAMI_BACKUP_RETENTION`, от 2 до 90). Если любая часть упала, недоделанный каталог удаляется: снимок либо целый, либо его нет.

## Стадия 2: зашифрованный пакет

Вторая стадия собирает пакет, которым можно поднять сервер с нуля, и по умолчанию выключена. Включает её файл `secrets/recovery.env`: скрипт читает его, только если это обычный файл, не ссылка, с правами ровно `600`; иначе он прекращает работу с сообщением «Refusing unsafe Minimal DR config». Если в файле нет открытого ключа `age`, стадии 2 и 3 пропускаются без ошибки.

Перед упаковкой скрипт проверяет входные данные. Снимок должен иметь манифест с `integrity: ok` и `secretsIncluded: false`, а каждый файл — совпадать с ним по SHA-256. Каждый исходный секрет — окружение Hermes, `github.env`, `tailortales-preview.env` и реестр `cron/jobs.json` — должен быть обычным файлом без прав для группы и остальных. Всё складывается во временный каталог с правами `700`, упаковывается `tar --zstd`, шифруется `age --encrypt --recipient`, рядом пишется файл `.sha256`. Существующий пакет перезаписать нельзя. Открытый текст удаляется всегда, в том числе при ошибке. Локально остаются три последних пакета.

## Стадия 3: загрузка с перечиткой

Третья стадия считает загрузку успешной только после того, как сама прочитала результат обратно. Скрипт сверяет локальную контрольную сумму, затем отправляет пакет и файл `.sha256` через `curl` с подписью AWS SigV4. Ключи доступа он передаёт через стандартный ввод, чтобы их не было в списке процессов. После этого скрипт проходит цепочку проверок.

```diagram
kind: sequence
desc: Скрипт отправляет пакет и контрольную сумму в S3, затем запрашивает размер объекта, читает контрольную сумму, смотрит список, удаляет самые старые пары и смотрит список ещё раз, чтобы убедиться, что осталось три пары.
actor script "Скрипт"
actor s3 "S3" external
msg script -> s3 "PUT пакет и .sha256"
msg script -> s3 "HEAD: размер"
self script "размер = локальному?"
msg script -> s3 "GET .sha256"
self script "сумма = локальной?"
msg script -> s3 "LIST: пара на месте?"
msg script -> s3 "DELETE старых пар"
msg script -> s3 "LIST: осталось три?"
```

Удаление старых пар ограничено: ключ записи в хранилище может только перечислять папку `recovery/` и читать, писать и удалять текущие объекты в ней. Права `DeleteObjectVersion` у него нет, поэтому включённое версионирование бакета сохраняет удалённый объект, а правило жизненного цикла стирает старые версии через 30 дней. Этот запас нужен на случай, если сбой скрипта удалил лишнее.

## Расписание

Ключ `*/3` в поле «день месяца» означает дни 1, 4, 7, …, 31, а не «каждые 72 часа». Счёт начинается заново каждый месяц, поэтому интервалы неровные.

| Месяц | Последний бэкап месяца | До следующего |
|---|---|---|
| 31 день | 31-го | 1 день |
| 30 дней | 28-го | 3 дня |
| 29 дней | 28-го | 2 дня |
| 28 дней | 28-го | 1 день |

Самый длинный интервал — три дня, то есть 72 часа. Предел проверки здоровья — 84 часа, так что ложной тревоги о старом бэкапе расписание не вызывает.

::::example Бэкап 4 октября (данные выдуманы)
:::steps
- **Hermes** — в 03:15:00 запускает `kurami-state-backup.sh`.
- **Снимок** — создаёт `backups/backup-20261004T031500Z/` с пятью файлами: `orchestrator.db`, три копии конфигурации и `manifest.json`. Старейший снимок удаляется, остаётся 14.
- **Пакет** — в 03:15:03 кладёт в `recovery/` файл `kurami-recovery-20261004T031503Z.tar.zst.age` и `.sha256`. Внутри снимок, три файла секретов, реестр cron и манифест.
- **Загрузка** — отправляет пару в бакет, сверяет размер и сумму, удаляет четвёртую по счёту пару и проверяет, что осталось три.
- **Hermes** — присылает итог в канал обслуживания: имя снимка, число файлов, сколько снимков осталось, имя пакета и строку о загрузке.
:::

## Что может пойти не так

| Ситуация | Что делает Kurami | Что делаешь ты |
|---|---|---|
| `quick_check` базы не `ok` | первая стадия падает, снимок не создаётся, задание завершается ошибкой | разобрать базу; прошлые снимки целы |
| `recovery.env` с неверными правами | после снимка скрипт останавливается, пакета нет | исправить права на `600` |
| Секрет доступен группе или это ссылка | пакет не создаётся, локальный снимок остаётся | исправить права файла |
| Ключ `age` не задан | стадии 2 и 3 пропускаются без сообщения; в итоге нет строк о пакете | прочитать итог и добавить ключ |
| Размер или сумма в S3 не совпали | задание падает, локальный пакет остаётся | повторить, проверить ключи AWS |
| Бэкап старше 84 часов | проверка здоровья поднимает критичную проблему | разобраться, почему не идёт задание |

:::guarantees
- Снимок не содержит секретов: манифест помечен `secretsIncluded: false`, и пакет без этой пометки не собирается.
- Закрытый ключ `age` никогда не попадает на сервер и в бакет.
- Расшифрованные файлы не остаются на диске ни при успехе, ни при сбое.
- Пакет не перезаписывается и не считается загруженным, пока бакет не подтвердил размер и сумму.
- Ключи доступа к S3 не видны в списке процессов.
:::
