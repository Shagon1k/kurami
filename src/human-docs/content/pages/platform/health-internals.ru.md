Мониторинг — это короткий скрипт, который раз в несколько минут собирает состояние сервера, сравнивает его с прошлой проверкой и только по итогу сравнения пишет в Discord.

:::glance
- Что делает: собирает метрики, ведёт серии по каждой проблеме и решает, слать ли тревогу, напоминание или сообщение о восстановлении
- Запускается: заданием Hermes `kurami-system-health`, по умолчанию каждые 20 минут, интервал меняешь ты
- Где работает: скрипт `kurami-runtime-health.sh`, без агента и без LLM; в Discord пишет сам, напрямую
- Состояние: четыре JSON-файла в `$KURAMI_HOME/state` — серии, счётчик OOM, история, id карточки
- Что видно: одна карточка, которую правят на месте, и отдельные сообщения в канале тревог
:::

## Сборщики

Скрипт читает всё сам, за один проход, и не меняет ничего на сервере. Сервер он измеряет напрямую: нагрузку CPU берёт из `/proc/stat` двумя замерами с паузой в 5 секунд, память из `/proc/meminfo`, счётчик убитых ядром процессов из `/proc/vmstat`, плюс load average и время работы. Сеть проверяют три HTTPS-запроса к Cloudflare, Google и GitHub.

Базу Run Store скрипт открывает только на чтение и запускает `PRAGMA quick_check`. Дальше он спрашивает Docker, сколько контейнеров работает и какие нездоровы, смотрит самые прожорливые процессы командой `ps` и сверяет превью: у каждой аренды должен быть проект Docker и каталог, а у каждого каталога — аренда. Наконец, он читает возраст самого свежего бэкапа и состояние ограничителя ресурсов: место на диске, число рабочих копий, карантин.

Два файла скрипту готовят другие: `cpu-statistics.json` пишет фоновый сэмплер CPU (запись каждые 15 секунд, в файле не больше 1440 точек), а `network-speed.json` — отдельное задание с замером скорости. Из них на карточку попадают скользящее среднее за 8 минут, пик и скорость. Для тревог среднее не используется: оно сглаживало бы длительную перегрузку, поэтому решает только 5-секундный замер.

## Проблемы, ключи и серии

Каждое нарушение превращается в *проблему* с тремя полями: ключом, серьёзностью и числом проверок подряд, которое нужно для подтверждения. Ключ держит проблему «той же самой» от проверки к проверке. Для CPU, RAM и сети ключи фиксированные: `server:cpu`, `server:memory`, `server:network`. Для остального ключ строится из текста сообщения, где числа заменены на `#`: «бэкапу 90 часов» и «бэкапу 91 час» дают один ключ.

| Проблема | Серьёзность | Проверок подряд |
|---|---|---|
| CPU от 85 % / от 95 % | warning / critical | 3 / 2 |
| RAM от 80 % / от 90 % | warning / critical | 3 / 2 |
| Сеть: отвечает 1–2 из 3 проб / ни одна | warning / critical | 3 / 2 |
| OOM-killer убил процесс с прошлой проверки | critical | 1 |
| `quick_check` не `ok`, Docker не rootless, нездоровые контейнеры | critical | 1 |
| Бэкап старше 84 часов (предел настраивается от 24 до 168) или его нет | critical | 1 |
| Несогласованные превью: сирота, провал аренды, лишний каталог | critical | 1 |
| Диск от 85 %, лимит рабочих копий, карантин | critical | 1 |
| Диск от 75 %, просроченный обзор карантина | warning | 1 |

Серия растёт, пока серьёзность проблемы не меняется. Если RAM перешла из warning в critical, серия начинается с единицы: критичная проблема должна подтвердиться своими проверками. Выпавшая проблема пропадает из серий сразу. Поэтому одиночный всплеск CPU на 97 % остаётся только строкой на карточке, а не тревогой.

## Решение: слать или нет

Решение принимает чистая функция. Она получает прошлое состояние, текущие проблемы и время и возвращает один из четырёх ответов. Сначала она обновляет серии. Проблема становится *активной*, когда серия дотянулась до нужной длины, и остаётся активной, пока присутствует в списке. Затем функция сравнивает *отпечаток* — отсортированный список пар «ключ:серьёзность» активных проблем — с прошлым.

```diagram
kind: graph
title: Какое сообщение отправить
desc: После обновления серий функция сравнивает отпечаток активных проблем с прошлым. Изменился и есть активные — тревога. Изменился и активных не осталось — восстановление. Не изменился, есть активные и прошло 120 минут — напоминание. Иначе сообщения нет.
node streak "Серии обновлены" at 0,0
node fp "Набор изменился?" decision at 1,0
node now "Есть активные?" decision at 0,1
node due "Прошло 120 минут?" decision at 2,1
node alert "Тревога" "alert" at 0,2
node recovery "Восстановление" "recovery" at 1,2
node reminder "Напоминание" "reminder" at 2,2
edge streak -> fp
edge fp -> now "да"
edge fp -> due "нет"
edge now -> alert "да"
edge now -> recovery "нет"
edge due -> reminder "да"
```

Восстановление приходит при *первой* же чистой проверке, без задержки. Такой выбор сделан осознанно: тревога не должна висеть дольше, чем проблема, а повторный всплеск всё равно пройдёт через серию. Шаг «Тревога» посылает и предупреждения: заголовок зависит от того, есть ли среди активных проблем критичная.

## Файлы состояния

| Файл | Что хранит | Кто читает |
|---|---|---|
| `runtime-health-alert.json` | серии по ключам, активные проблемы, время последнего сообщения | следующая проверка |
| `runtime-health-counters.json` | счётчик убитых ядром процессов | следующая проверка: разница даёт «OOM killer terminated N processes» |
| `system-health-history.json` | десять последних проверок | список «Inspect one of the last 10 runs…» |
| `system-health-discord.json` | канал и id сообщения-карточки | следующая проверка, чтобы править то же сообщение |
| `health-settings.json` | интервал, ревизия, кто и когда изменил | форма настроек и команда смены интервала |

Все файлы пишутся атомарно: сначала временный файл, потом переименование. Поэтому обрыв посреди записи не оставляет половину JSON.

## Доставка в Discord

Задание Hermes помечено `deliver: local`, и Hermes сам ничего не публикует. Сообщения отправляет скрипт напрямую через REST Discord. Так карточка не получает «Cronjob Response» в заголовке, а сама карточка — это не новое сообщение, а правка старого.

Сначала скрипт доставляет тревогу и только после успеха записывает новое состояние серий. Если отправка не удалась, состояние остаётся прежним, и следующая проверка примет то же решение. Чтобы повтор не родил дубль, каждое сообщение несёт *nonce* — одноразовую метку, построенную из вида сообщения, времени прошлого сообщения и отпечатка. Discord с включённой проверкой nonce отбрасывает второе сообщение с той же меткой. Каждый запрос пробуется до трёх раз, ответ 429 скрипт выжидает до пяти секунд.

После тревоги скрипт дописывает запись в историю и правит карточку. Если карточку удалили, Discord отвечает 404, и скрипт публикует новую и запоминает её id.

## Чего мониторинг не видит

Мониторинг не следит за самим собой. Если Hermes остановился или падает скрипт, задание не сообщит об этом: его доставка локальная, а сторожа для сторожа нет. Единственный признак — время «Updated» на карточке, которое перестаёт меняться. Нагрузка контейнеров по порогам не оценивается: она показана среди «прожорливых» и тревогу не вызывает.

| Проверка | RAM | Серия `server:memory` | Решение | Что видно в Discord |
|---|---|---|---|---|
| 10:00 | 79 % | нет | тишина | карточка зелёная |
| 10:10 | 83 % | warning 1/3 | тишина | карточка жёлтая, строка в Issues |
| 10:30 | 86 % | warning 3/3, активна | `alert` | «⚠️ Warning», «Top consumers at alert time» |
| 12:30 | 86 % | активна, прошло 120 минут | `reminder` | «⏰ Reminder» |

Между 10:10 и 10:30 карточка уже «жёлтая», но владельца никто не зовёт: два первых предупреждения ещё не подтверждены.

## Что может пойти не так

| Ситуация | Что делает Kurami | Что делаешь ты |
|---|---|---|
| Discord недоступен | скрипт пробует три раза и завершается с ошибкой; состояние серий не сдвигается | ничего: следующая проверка повторит то же решение |
| Карточка удалена | получает 404, публикует новую и запоминает её id | ничего; лишние сообщения в канале убирает флаг `--cleanup-health-channel` |
| Hermes остановлен | проверки не запускаются; тревоги нет | заметить застывшее «Updated» и проверить `hermes-gateway` |
| Смена интервала отклонена | Hermes не принял расписание, форма говорит об ошибке, интервал прежний | повторить или проверить идентификатор задания |
| Задание пересоздано после аварии | у него новый идентификатор, а форма настроек ищет старый | задать `KURAMI_HEALTH_JOB_ID` |

:::guarantees
- Мониторинг только наблюдает: он не чинит, не удаляет превью и не останавливает запуски.
- Короткий всплеск не превращается в тревогу: нужна серия подряд.
- Повтор после сбоя не создаёт второго сообщения: одинаковый nonce отбрасывается Discord.
- Каждая проблема сообщается один раз на изменение, а не на каждую проверку.
:::
