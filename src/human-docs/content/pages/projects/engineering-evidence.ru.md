Доказательство в Kurami — это результат проверки одного конкретного коммита PR: CI, AI-ревью или исправления. Каждое хранит SHA этого коммита и перестаёт считаться, когда коммит меняется.

:::glance
- Что делает: читает CI коммита PR, а по твоей кнопке запускает исправление CI, независимое AI-ревью и исправление замечаний
- Кто запускает: наблюдатель CI — каждую минуту сам; всё остальное — ты кнопкой
- Где работает: короткие скрипты контроллера; ревьюер — отдельная tmux-сессия `rv-…`
- Состояние: `run_ci_snapshots`, `run_ci_repair_attempts`, `run_ai_reviews`, `run_review_fix_rounds` в Run Store
- Пределы: 2 попытки исправить CI, до 10 замечаний в ревью, 10 минут ждать новый коммит, 30 минут ждать CI, 90 минут на процесс
- Что видишь: поля CI и AI review на карточке, нативное ревью `kurami-ai[bot]` в PR
:::

## Привязка к коммиту

Kurami привязывает каждое доказательство к SHA, потому что агент продолжает пушить: зелёный CI на коммите A ничего не говорит о коммите B. Поэтому у каждого вида проверки есть своё поле с SHA и свой способ отбросить устаревший результат.

| Доказательство | Где хранится SHA | Что его обесценивает |
|---|---|---|
| Снимок CI | `run_ci_snapshots.head_sha`: проверки читаются именно на этом коммите | любой новый пуш заменяет снимок |
| Исправление CI | `source_head_sha`: рабочая копия должна стоять на нём | успехом считается только новый коммит с зелёным CI |
| AI-ревью | `base_sha` и `head_sha`, скрытые метки `head=<sha>` в ревью и в каждом комментарии | коммит сдвинулся — на карточке «Outdated»; сдвинулся во время ревью — «Superseded», ничего не публикуется |
| Исправление замечаний | `source_head_sha` снимка; `result_head_sha` результата | потоки с меткой другого коммита не берутся |
| Превью | `verified_head_sha` аренды превью | наблюдатель CI сбрасывает отметку, если у превью другой SHA |
| Завершение | коммит слитого PR совпадает с HEAD копии | — |

Кнопки, которые запускают эти проверки, описаны в [Управлении из Discord](@owner-controls). Как доказательство слияния работает при завершении — в [Завершении и очистке](@release-cleanup), а доказательство превью — в [Как работают превью](@preview-internals).

## Наблюдение за CI

В Projects открой карточку задачи и раскрой **Проверки** под CI. Нажать можно в любом месте строки «Проверки». Каждая проверка занимает одну строку: иконка результата и название со ссылкой на джобу GitHub, если она доступна. Длинные названия обрезаются; полное имя и результат остаются в подсказке и тексте для скринридера. При ошибке или отсутствии проверки список открыт сразу. В таблице задач остаётся только общий статус CI.

Список берётся из сохранённого снимка наблюдателя CI, с коммитом и временем наблюдения. Обновления карточки сохраняют твой выбор раскрытия для этого коммита. Для отсутствующей проверки ссылка не придумывается; недоступные подробности не означают успешный CI.

Наблюдатель CI раз в минуту находит для ветки запуска единственный открытый PR и читает его проверки на коммите. Так CI оценивается независимо от Codex и от Discord: наблюдатель только читает GitHub и пишет строку в `run_ci_snapshots`.

Он вызывает GitHub REST, берёт check-runs и статусы коммита и учитывает только *обязательные* проверки из `projects.yaml` — точные имена, например `Secret scan` и `Lint, type-check, test` у TailorTales. Для каждого имени берётся самая свежая запись. Итог складывается по приоритету: `failed`, затем `unknown`, `pending`, `missing`, и только потом `passed`.

| Итог | Значение |
|---|---|
| `passed` | все обязательные проверки зелёные на этом коммите |
| `failed` | хотя бы одна упала, отменена, по таймауту или требует действия |
| `pending` | проверки идут; отсутствующие тоже считаются `pending` первые 10 минут (`missing_grace_minutes`) |
| `missing` | обязательной проверки нет уже 10 минут |
| `unknown` | несколько открытых PR у ветки, ошибка GitHub или неизвестный статус |

Строка снимка одна на запуск и перезаписывается. Дайджест содержимого позволяет карточке заметить изменение, а `first_observed_at` сбрасывается вместе с новым коммитом, чтобы отсчёт льготных 10 минут шёл заново.

## Исправление CI

Исправление CI — это до двух свежих задач Codex, каждая по твоей кнопке **Attempt CI fix**. Кнопка есть, когда CI `failed` или `missing`, запуск стоит в `parked_review`, тред известен и попыток меньше двух. Лимит два ограничивает расход и цикл «чиним — снова красный»; после второй красной попытки решаешь ты.

Контроллер проверяет, что рабочая копия чиста и стоит ровно на `source_head_sha`, иначе отказывается. Затем запускает новую сессию с промптом: вот SHA, вот упавшие проверки как недоверенные данные, прочитай логи через `gh`, сделай минимальное исправление, закоммить и запушь в ту же ветку. Промпт запрещает force-push, rebase, слияние и второй PR. Когда Codex закончил ход, контроллер освобождает сессию, а задача ждёт CI.


Ограничения времени такие: нет нового коммита 10 минут после парковки исполнителя — `needs_attention` (`ci_repair_no_new_head`); коммит есть, но CI не определился 30 минут — `ci_repair_ci_timeout`. Пока попытка идёт, Take control недоступен. Когда она закончена, контроллер архивирует технический тред и возвращает основной.

Упавшая проверка security audit разрешает минимальное совместимое исправление зависимости из опубликованной upstream-версии или точечный override транзитивной зависимости. Codex проверяет advisory, опубликованную версию, совместимость с потребителями и соответствующие тесты. Посторонние обновления, major-версии, собственные патчи и форки, исключения advisory, ослабление audit policy, миграции, изменения границ безопасности, секретов и прав остаются вне scope. Без совместимого опубликованного исправления Codex останавливается и сообщает блокер.

Для протокольного исполнителя статус run-control, Discord и Projects сохраняют ограниченный итоговый отчёт отдельно от результата доставки. Завершённый отказ без изменений поэтому объясняет отсутствие нового PR head; это не падение исполнителя. Отчёт ограничен 800 символами, очищен и привязан к точным задаче, попытке, треду и ходу. Принимается только финальный ответ ассистента. Вывод команд, ошибки, промпты и восстановленный основной разговор исключены. Отсутствующий отчёт явно недоступен; при падении сохраняется протокольный код ошибки. Отчёт не меняет владельца или доступность повторной попытки.

## AI-ревью

AI-ревью — это независимый read-only проход Codex по diff между базой PR и его коммитом, который публикуется как одно нативное ревью GitHub. Ты запускаешь его кнопкой **AI Code Review** в спокойном состоянии, когда рабочей копией никто не владеет. Ревью можно запустить, пока CI ещё идёт: оно ничего не пишет.

Контроллер проверяет, что у ветки ровно один открытый PR с ожидаемой базой, а HEAD копии равен коммиту PR. Если у этого коммита уже есть готовое ревью, повторное не запускается. Ревью выполняет отдельная tmux-сессия `rv-tt-42-3f9a1c-1`, у неё нет `GH_TOKEN`: скрипт получает краткоживущий токен GitHub App `kurami-ai`, читает PR и задачу и передаёт их Codex как данные. Дочерний Codex запускается в песочнице `read-only` без подтверждений, из его окружения удалены все переменные с секретами, а любой запрос разрешения отклоняется и считается ошибкой.

Codex обязан вернуть JSON: краткое резюме и до десяти замечаний с серьёзностью (`critical`, `important`, `suggestion`), уверенностью, файлом и строкой. Скрипт отклоняет ответ, если в нём есть похожие на секреты строки, больше десяти замечаний или небезопасный путь. Перед публикацией он ещё раз сверяет PR, базу, коммит и чистоту копии. Замечания на изменённых строках уходят встроенными комментариями, остальные — в тело ревью. Ревью всегда публикуется как `COMMENT`, без одобрения и запроса изменений. На карточке появляются `N Critical · N Important · N Suggestions`.

Промпт ревью сопоставляет вероятность и последствия с реальными требованиями. Для предлагаемых дополнений нужны конкретный сценарий, последствия и минимально достаточное исправление. Малозначимые гипотезы не блокируют работу, а допустимые ограничения не считаются дефектами; безопасность, авторизация, целостность данных и явные критерии приёмки сохраняются.

Простота не задаёт квоту замечаний. Замечание о сложности требует доказанного ущерба сопровождаемости или корректности, внесённого этим diff, и соразмерного упрощения. Меньшее число строк или предпочтение стиля сами по себе не оправдывают замечание. Ревью без замечаний допустимо; режим только для чтения, точный SHA и формат JSON остаются прежними.

## Исправление замечаний ревью

Исправление замечаний — это свежая задача Codex, которая правит ровно те ветки обсуждения, которые были нерешены в момент твоего нажатия **Fix Review**. Кнопка есть, если готовое ревью текущего коммита содержит хотя бы одно замечание.

Контроллер делает неизменяемый снимок: нерешённые и не устаревшие потоки, у которых первый комментарий оставил `kurami-ai` с меткой текущего коммита или ты сам. Твои ответы внутри потока становятся уточнением. Потоков не больше двадцати. Комментарии, добавленные позже, попадут в следующий раунд. Codex получает снимок как данные и обязан запушить исправление, но не отвечать в потоках и не ждать CI.

Дальше Kurami сам ведёт раунд. Когда появляется новый коммит с зелёным CI, бот `kurami-ai` отвечает в каждом потоке «Fixed by Kurami in `<sha>` after CI passed», а поток закрывается. Закрывает его твой токен: GitHub разрешает это только автору PR или пользователю с правом записи, а бот такого права не имеет. Токен не попадает ни в Codex, ни в ревьюера. Попыток закрыть потоки три.


## Что может пойти не так

| Ситуация | Что делает Kurami | Что делаешь ты |
|---|---|---|
| Обязательная проверка не появилась | через 10 минут итог `missing`, доступен Attempt CI fix | чинишь workflow или пробуешь Attempt CI fix |
| Открыто несколько PR у ветки или GitHub не ответил | итог `unknown`, причина в снимке; исправление недоступно | закрываешь лишние PR, ждёшь |
| После исправления CI нет нового коммита 10 минут | попытка и запуск в `needs_attention` | берёшь управление |
| Вторая попытка тоже красная | запуск в `needs_attention` (`ci_repair_attempt_budget_exhausted`) | чинишь руками |
| PR сдвинулся во время ревью | ревью `superseded`, ничего не опубликовано | запускаешь AI Code Review заново |
| Процесс ревью пропал | через 15 секунд ревью `failed` | запускаешь заново |
| Ответ ревьюера похож на секрет или невалиден | ревью `failed`, ничего не опубликовано | запускаешь заново |
| Codex оставил несохранённые правки, не продвинув коммит | раунд и запуск в `needs_attention`, работа сохранена | забираешь работу руками |
| Codex запушил, а терминал остался «грязным» | кнопка **Recover delivered fix**, если коммит, CI и сессия совпадают | нажимаешь её |
| Пуш пришёл позже 10 минут ожидания | раунд возвращается сам, запуск снова `parked_review` | ничего |
| Закрыть потоки не удалось три раза | раунд и запуск в `needs_attention` | чинишь права; оператор повторяет только закрытие потоков |
| Процесс работает дольше 90 минут | остановка, запуск в `needs_attention`, всё сохранено | смотришь хвост терминала |

:::guarantees
- Kurami считает доказательством только результат для текущего коммита PR.
- Наблюдатель CI только читает GitHub: он не меняет PR, ветку и проверки.
- Исправление CI, AI-ревью и Fix Review начинаются только по твоей кнопке; автоповторов нет, попыток исправления CI две.
- Ревьюер работает без записи и без секретов, любой его запрос разрешения отклоняется, а публикует он только `COMMENT`, без одобрения.
- Codex-исправитель не отвечает в потоках и не закрывает их; это делает Kurami после зелёного CI и только для потоков снимка.
:::

- `src/orchestrator/runtime/reconcile-ci-repair.ts` — состояния попытки исправления CI и таймауты
- `src/orchestrator/projects/reviews/manager.ts` — запуск ревью и проверки перед ним

## Восстановление оператором после внешнего исправления PF-34

PF-34 / PR #157 — отдельный случай внешней доставки с разрешения владельца.
Завершённый CI-исполнитель не создал новый head; архивная попытка остаётся
`needs_attention`, с исходным `c442192ed8aa4eccc25e06bd90874cc9d1adf7a5` и null result.
Внешнее исправление доставило `b46c7eb16912198596b45d075d5e4f9610671387` с шестью
успешными проверками. Только привязанный к инциденту операторский CLI
`recover-external-ci-delivery.ts` возвращает запуск в `parked_review`; зелёный CI
сам по себе не снимает остановку. По умолчанию dry-run проверяет точные receipts,
