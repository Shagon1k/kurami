Projects Digest — это конвейер, который превращает доску GitHub Project в одну карточку с предложением «что взять следующим». Выбор делает обычная формула по сохранённым фактам, а ИИ только предлагает заполнить пустые поля и ничего не пишет сам.

:::glance
- Что делает: собирает факты доски, выбирает задачу по формуле, показывает карточку и ведёт пакеты предложений Priority и Effort
- Кто запускает: ежедневная задача Hermes в 06:45 UTC и минутный опрос, когда доска изменилась
- Ритм: факты и карточка — раз в сутки и по событию; ИИ-пакет — не чаще раза в сутки на проект
- Состояние: `project_triage_state`, `project_triage_rankings`, `project_metadata_proposal_batches`
- Где работает: скрипт Projects Digest; ИИ — отдельный процесс Codex только для чтения
- Видно тебе: карточка проекта в канале Digest с кнопками пакета
:::

## Снимок фактов

Снимок — это сохранённая копия того, что доска говорит о каждой задаче проекта, вместе с выводом «готова ли она к запуску». Сборщик читает GitHub Project постранично. Для каждой задачи он берёт статус, Priority, Effort, метки, признак описания, блокирующие и блокируемые задачи. Затем он считает хеш фактов без временных меток. Если хеш тот же, обновляется только `last_checked_at`. Если он новый, в `project_triage_snapshots` добавляется строка с очередным `change_sequence`. Так ранжирование и ИИ запускаются, только когда факты действительно изменились.

Задача попадает в выбор, только если у неё нет ни одной причины отказа. Причины хранятся списком, поэтому видно, почему задача не готова.

| Причина | Значение |
|---|---|
| `not_issue`, `repository_mismatch` | элемент доски не задача этого репозитория |
| `issue_not_open` | задача закрыта |
| `not_backlog` | задача не в колонке Backlog |
| `needs_clarification` | нет описания |
| `blocked_by_open_issue` | её блокирует открытая задача |
| `active_run_exists` | по ней уже идёт запуск |
| `unsupported_runtime` | у проекта нет рабочей копии и базовой ветки в конфигурации |

## Ранжирование

Ранжировщик присваивает каждой готовой задаче число и берёт наибольшее. Формула `deterministic-v2` складывает три слагаемых: уровень приоритета, малость оценки и возраст. Приоритет весит на порядок больше остального, поэтому приоритет, поставленный тобой, всегда решает выбор первым.

| Слагаемое | Значения |
|---|---|
| Priority | P0 — 5000, P1 — 4000, P2 — 3000, P3 — 2000, P4 — 1000; слова critical и urgent — 5000, high — 4000, medium — 3000, low — 2000; пусто — 0 |
| Effort | XS — 40, S — 32, M — 22, L — 10, XL — 0; число n даёт 40 − 5·min(n, 8) |
| Возраст | число полных дней с создания, не больше 30 |

При равной сумме побеждает больший приоритет, затем меньшая оценка, больший возраст, меньший номер задачи. Зависимости очков не добавляют: открытая блокировка лишь делает задачу неготовой. Строка «Owner priority P1 · Effort M · Waiting 9 days · Ready to start» на карточке собирается из тех же чисел, поэтому объяснение не расходится с выбором. Результат записывается в `project_triage_rankings`; поле `suggested_since` сохраняется, пока выбрана та же задача.

## Карточка Digest

Карточка проекта — одно сообщение, которое Kurami правит на месте. Программа карточки считает отпечаток из рейтинга, счётчиков, даты последней проверки, номера снимка и состояния пакета предложений. Если он совпал с сохранённым, ничего не происходит. Поэтому «Checked» сдвигается не чаще раза в сутки, а между проверками карточка не мигает. Как карточка выглядит и какие на ней кнопки — в [Projects Digest](@project-digest), имена кнопок — в [справочнике](@commands).

Есть два входа. Ежедневный запуск без аргументов собирает факты, ранжирует, запускает планировщик ИИ и рисует карточки. Событийный запуск для одного проекта делает то же самое, но планировщик пропускает. Минутный опрос вызывает его, когда изменилась доска или закончилась запись метаданных. Поэтому событие на доске обновляет карточку в течение минуты и не запускает ИИ.

## Пакет предложений

Пакет — это замороженный список задач Backlog, у которых пусты Priority или Effort. Планировщик отбирает кандидатов. Первый пакет проекта называется `bootstrap` и берёт все неоценённые задачи. Следующие пакеты `changed` берут только те, у кого изменились название, статус, поля, метки или описание. Кандидаты сортируются в порядке ранжирования и обрезаются по `ai_triage_daily` — 12 по умолчанию, от 0 до 40 (меняется в [Настройках](@settings)).

На проект допускается один пакет в сутки по UTC: дату записывает `project_metadata_daily_admissions`. Одновременно активен один пакет на проект. Если задача из активного пакета изменилась, новый пакет вытесняет старый (`superseded`). Оставшийся с прошлых суток пакет в состоянии `running` считается упавшим и заменяется новым. Планировщик не стартует, если управляемая нагрузка ИИ уже достигла `max_llm_running_global`.

## Как ИИ оценивает задачи

Работник задаёт Codex узкий вопрос и не доверяет ни вопросу, ни ответу. Он заранее читает каждую задачу через `gh api` и прерывает пакет, если название, описание или метки изменились после снимка. Затем он запускает отдельный процесс Codex только для чтения, без сети, инструментов и запросов разрешений. Текст задач передаётся как ненадёжные данные в безопасной обёртке, а не как инструкции. Пакет режется на части до 12 задач.

Ответ проверяется строго. Допускаются только поля из списка пустых, Priority P1–P3, Effort XS–XL, уверенность `high` или `medium`, до четырёх коротких доказательств; ответ с похожим на секрет текстом отвергается. P0 невозможен и на уровне базы. Ошибку формата Codex получает исправить ровно один раз, вторая ошибка переводит пакет в `failed`. Итоговый текст «N предложений для M задач» пишет код, а не модель.

## Решение и защищённая запись

Пакет проходит короткую цепочку состояний, и запись в GitHub возможна только в конце.

**Accept batch** только помечает предложения принятыми. Запись делает синхронизация на каждом минутном проходе. Для каждого поля он заново читает текущее значение в GitHub Project и решает по правилам ниже.

| Текущее значение в GitHub | Решение |
|---|---|
| совпадает с предложением | считается применённым, запись не нужна |
| пусто | записывается предложенное значение |
| равно значению, которое Kurami записал раньше | записывается предложенное значение |
| любое другое | конфликт: значение владельца остаётся |
| предложено P0 | отказ |

Записанное значение запоминается в `project_metadata_field_ownership`, поэтому позже Kurami отличает своё значение от твоего. Временная ошибка GitHub откладывает пакет и даёт ещё одну автоматическую попытку. После двух неудач на карточке появляется **Retry sync**.

::::example Пакет предложений для PickFlick
В Backlog шесть задач без Priority или Effort, `ai_triage_daily = 12`. Данные придуманы.
:::steps
- **Digest** — в 06:45 UTC собирает снимок: `change_sequence` 17, выбирает PF-31 («Owner priority P1 · Effort M · Waiting 9 days»).
- **Планировщик** — пакета ещё не было, поэтому создаёт `bootstrap`-пакет №1 из шести задач и записывает допуск на эту дату.
- **Работник** — читает шесть задач, просит Codex оценить и получает семь предложений. Пакет становится `ready`, карточка пишет «Ready · 7 pending».
- **Ты** — в 09:10 открываешь Review proposals, исключаешь предложение P1 для PF-52 и нажимаешь Accept remaining. Шесть предложений принято, пакет `accepted`.
- **Синхронизация** — в 09:11 пять полей пусты и записаны. У PF-44 ты вчера сам поставил Effort L: значение не пусто и записано не Kurami, поэтому предложение получает `conflicted`.
- **Digest** — обновляет карточку: «Partially applied · 5 applied», «1 owner values preserved».
:::

## Что может пойти не так

| Ситуация | Что делает Kurami | Что делаешь ты |
|---|---|---|
| GitHub недоступен при сборе фактов | скрипт завершается с ошибкой, прежняя карточка остаётся | ничего: следующий запуск повторит |
| Codex вернул некорректный ответ дважды | пакет `failed` | ждёшь следующих суток |
| Задача изменилась после снимка | пакет `superseded`, будет создан новый | ничего |
| Работник упал, пакет висит в `running` | на следующие сутки пакет закрывается и заменяется | ничего |
| Нет свободной нагрузки ИИ | планировщик пропускает день по проекту | ничего |
| Поле изменил ты | предложение получает `conflicted`, твоё значение остаётся | ничего |
| GitHub ответил ошибкой при записи | одна автоматическая повторная попытка, затем Needs attention | нажимаешь Retry sync |
| Тред обсуждения нельзя архивировать | Accept и Skip отказывают | закрыть тред и нажать снова |

:::guarantees
- ИИ работает только для чтения: без сети, инструментов, разрешений и записи в GitHub.
- Итоговое предложение выбирает формула, а не модель.
- Kurami не предлагает P0 и не выводит зависимости.
- Accept ничего не пишет в GitHub: запись идёт отдельно и по правилам таблицы.
- Значение, которое ты поставил сам, не перезаписывается.
- На проект приходится не больше одного пакета в сутки и одного активного пакета.
:::
