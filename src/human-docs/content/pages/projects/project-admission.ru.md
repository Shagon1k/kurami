Допуск — это проверка, которая решает, станет ли перенос карточки в In progress запуском. Он только записывает решение в базу: Git, tmux и Codex допуск не трогает. Тот же скрипт разбирает и остальные переносы — в Human Review, Done, Backlog и Deferred; их следствия описаны в [Жизненном цикле запуска](@run-lifecycle).

:::glance
- Что делает: берёт события из очереди и для каждого создаёт запуск, отказ или игнорирует событие
- Кто запускает: минутный цикл, под общей блокировкой
- Где работает: одна транзакция SQLite на всю пачку событий
- Состояние: `runs` и `run_resources` (план ветки и рабочей копии), `run_state_history`
- Лимиты: общий WIP 2, WIP проекта 2, шесть рабочих копий, диск ниже 85 %
- Что видно: карточка запуска в Discord или запись об отказе с причиной
:::

## Проверки по порядку

Перед обработкой переноса потребитель проверяет метки задачи, записанные в событии. При `no-auto` он помечает событие как проигнорированное и не выполняет действия жизненного цикла. Для независимой задачи нет запуска, отказа или плана ресурсов.

Допуск применяет шесть проверок в фиксированном порядке. Проверки 1–3 игнорируют событие с записанной причиной и запуск не создают. Проверки 4 и 5 создают запуск `rejected`, чтобы причина осталась видна.

| № | Проверка | Если не прошла |
|---|---|---|
| 1 | Это задача (issue), а не черновик или PR, из репозитория проекта | Событие игнорируется |
| 2 | Задача открыта и имеет непустое описание | Событие игнорируется |
| 3 | Живого запуска для этой карточки ещё нет | Событие игнорируется: «Live run already exists» |
| 4 | Лимиты WIP не исчерпаны | Запуск `rejected`: `WIP limit reached: global X/Y, project A/B` |
| 5 | Защита ресурсов не блокирует допуск | Запуск `rejected`: `Resource guard blocked admission: …` |
| 6 | Всё прошло | Запуск `admission_pending` с запланированными ресурсами |

Живой запуск — любой, кроме `rejected`, `cancelled` и `archived`. Поэтому карточка, вернувшаяся из Human Review в In progress, новый запуск не создаёт: старый ещё на паузе ревью. Допуск судит по тому, что записано в событии: открыта ли задача, есть ли описание, какие метки. GitHub он не перечитывает. Как отказ выглядит в Discord и что с ним делать — в [Статусах доски](@board-statuses).

## Как считается WIP

WIP — это число запусков, которые сейчас занимают место, и допуск считает их по состоянию. Считаются `admission_pending`, `starting`, `running`, `remote_owned`, `stopping` и `needs_attention`. Запуск на паузе ревью (`parked_review`) **не считается**: он ждёт тебя и не должен блокировать новые задачи. Но он остаётся живым, поэтому второй запуск для той же задачи создать нельзя.

Лимитов два: общий (`max_active_global`, по умолчанию 2) и на проект (`max_active_per_project`, по умолчанию 2). Оба ты меняешь в [настройках](@settings) и только в простое. WIP считает запуски, а не физические ресурсы: их ограничивают отдельно — лимит одновременных Codex (по умолчанию один) и защита ресурсов.

## Защита ресурсов

Защита ресурсов — это осмотр сервера перед каждым допуском. Она нужна, потому что неучтённый каталог или tmux-сессия могут быть твоей работой. Kurami ничего из них не удаляет, а блокирует допуск и зовёт тебя.

Защита сравнивает три вещи. Каталоги внутри корня рабочих копий проекта — с теми, что записаны в `run_resources`. Записанные рабочие копии — с диском: нет ли пропавших. tmux-сессии `cx-…` — с теми, что принадлежат запускам. Допуск блокируется, если диск занят на 85 % и больше, если рабочих копий шесть (на проект — четыре), если есть хоть одно расхождение или хоть один активный карантин.

```diagram
kind: graph
title: Жизненный цикл карантина
desc: Расхождение впервые замечено и получает состояние observed. Если оно остаётся дольше тридцати минут, оно переходит в quarantined. Когда расхождение исчезает, карантин переходит в resolved. Через семь дней карантин требует твоей проверки.
node observed "observed" "замечено" state at 0,0
```

Каждый шаг пишет событие в `resource_guard_events`, а уведомитель собирает их в сообщения в канале оповещений: по шесть событий, без упоминаний, без повторов после перезапуска. Кнопки очистки нет. Разобраться с ресурсом ты можешь только сам; когда расхождение исчезнет, карантин закроется.

## Имена запуска

Допуск придумывает запуску имена заранее, чтобы ресурсы можно было проверять ещё до их создания. Идентификатор запуска — `r_` и первые двадцать знаков sha256 от идентификатора события; одно событие создаёт не больше одного запуска. Имя ветки — префикс проекта, номер задачи и до шести слов заголовка, если он вида `[Feature]: Add dark mode toggle`. Слова приводятся к латинице, «a», «the», «to», «for», «of», «and» отбрасываются, длина не больше 48 знаков. Если такая ветка или каталог уже были, добавляется `_retry-2`, `_retry-3`. Рабочая копия лежит в `<корень проекта>/<ветка>/<имя репозитория>`.

Метка `human-control` на issue даёт `interaction_policy = human_control`, иначе `autonomous`. Метка `preview-required` включает `preview_required`. Режим `execution_mode` берётся из `orchestrator.yaml`: `live` или `dry_run`. В dry-run допуск создаёт запуск, но ни одна рабочая копия не появится.

::::example Два переноса подряд
:::steps
- **Допуск** — задача TT-42 «[Feature]: Add dark mode toggle»: issue открыт, описание есть, живого запуска нет, WIP 0 из 2, диск 41 %. Создаётся `r_26d6bafe366257202f23` в состоянии `admission_pending` и план: ветка `TT-42_add-dark-mode-toggle`, каталог `<worktree_root>/TT-42_add-dark-mode-toggle/TailorTales`.
- **Допуск** — через три часа ты переносишь TT-43, когда запущены TT-40 и PF-12. Общий WIP равен 2 из 2.
- **Допуск** — создаёт запуск в состоянии `rejected` с причиной `WIP limit reached: global 2/2, project 1/2`. Ресурсов у него нет.
- **Ты** — заканчиваешь TT-40, переносишь TT-43 в Backlog и снова в In progress. Это новое событие и новый запуск со ссылкой на отклонённый.
:::

## Что может пойти не так

| Ситуация | Что делает Kurami | Что делаешь ты |
|---|---|---|
| Допуск падает с ошибкой (неверный конфиг, база занята дольше пяти секунд) | Транзакция откатывается, события остаются в очереди. Скрипт завершается с кодом 1, и в эту минуту контроллер тоже не работает | Посмотри `project-event-consumer-errors.log` и исправь настройки |
| Лимиты ресурсов меньше лимитов запусков | Допуск отказывается работать: рабочих копий должно быть не меньше общего WIP | Исправь `orchestrator.yaml` |
| Все запуски отказываются с `Resource guard blocked admission` | Любое расхождение блокирует допуск во всех проектах, пока не исчезнет | Найди каталог или tmux-сессию из причины и разберись руками |
| Отказ из-за WIP | Запуск `rejected`, ресурсов нет, повторов нет | Освободи место и перенеси карточку заново |
| Диск выше 85 % | Новые запуски отклоняются, существующие продолжаются | Освободи диск |

:::guarantees
- Допуск ничего не создаёт в Git, tmux и Codex: он записывает решение в базу.
- Для одной карточки не бывает двух живых запусков: это гарантирует уникальный индекс, а не только проверка.
- Отказ не ставится в очередь и не повторяется сам.
- Защита ресурсов только наблюдает и сообщает: она никогда не удаляет и не чинит ресурс.
:::
