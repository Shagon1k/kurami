Kurami Orchestrator — руководство по системе

Kurami превращает явные действия владельца в GitHub Project в управляемую инженерную работу. Он координирует Git, Codex, CI, preview и Discord, сохраняет состояние между перезапусками и останавливается, когда не может доказать безопасность следующего шага.

Release: P9 · guide + readiness E2E baseline: e4ffec0 Schema: 30 Control plane: Discord Projects: TailorTales + PickFlick

Общая модель

Это не один большой бот. Это несколько независимых подсистем, соединённых SQLite-состоянием и точными идентификаторами run, branch, worktree, PR и preview.

01 · Намерение

GitHub Project

Owner меняет статус issue. Это единственный обычный вход для начала, отмены и завершения.

02 · Решение

Admission

Kurami проверяет проект, issue, актуальность snapshot, WIP, LLM и физические ресурсы.

03 · Работа

Isolated execution

Отдельные branch, worktree и Codex task. Canonical checkout не используется как workspace.

04 · Доказательства

PR, CI, review

Каждый результат связан с exact PR head SHA. Stale evidence не двигает lifecycle.

05 · Контроль

Discord + preview

Owner видит состояние и запускает только допустимые bounded actions.

06 · Завершение

Release or preserve

После merge ресурсы освобождаются. При сомнении работа сохраняется и требуется решение owner-а.

Подсистемы

Карточки можно читать в любом порядке. Основной слой объясняет роль подсистемы; раскрываемая часть содержит внутренний контракт и поведение при сбое.

Observation

Projects и приоритеты

Считывает намерение owner-а и даёт обзор Backlog без запуска лишней работы.

Получает: Project items, status, labels, Priority/Effort.
Отдаёт: durable events, ranked digest, metadata proposals.
Контракт и отказоустойчивость
Первый poll создаёт baseline, а не runs. Повтор без изменений — no-op. Сбой одного Project блокирует только новую работу этого проекта; reconciliation остальных runs продолжается. Metadata пишется лишь после owner acceptance и повторной проверки live drift.
Admission

Допуск и лимиты

Решает, можно ли безопасно начать новый writer прямо сейчас.

Получает: issue event, settings, project health, resource inventory.
Отдаёт: один admitted run либо объяснимый reject/wait.
Что проверяется
Open issue, правильный repo/status, непустое описание, отсутствие другого active run, свежий Project poll, project/global WIP, global LLM, worktree/tmux caps и disk thresholds. Решение и резервирование записываются одной SQLite transaction, поэтому параллельные poller-ы не создадут двух writers.
Execution

Git workspace и Codex

Изолирует изменение и гарантирует одного текущего автора.

Получает: admitted run и свежий base branch.
Отдаёт: exact branch/worktree, managed task и Draft PR.
Ownership и handoff
Canonical checkout остаётся clean. CLI, Remote и technical workers не могут одновременно владеть writer-ролью. Takeover сначала доводит текущую task до стабильной границы. Autonomous continuation создаёт новую linked task, а не возвращает ownership старой. Ambiguity останавливает запуск.
Evidence

CI и code review

Проверяет именно текущую версию PR и ограничивает автоматические исправления.

Получает: exact PR/head, required check names, review threads.
Отдаёт: normalized CI, bounded findings и новый доказанный SHA.
Почему exact SHA важен
Старый green check не доказывает новый commit. CI repair допускает максимум две отдельные owner-triggered попытки. AI review read-only и публикует не более десяти findings. Review fix работает только со snapshot текущих unresolved threads, затем ждёт CI и закрывает только этот snapshot.
Preview

Compose и static preview

Даёт owner-у проверяемый результат без прямого production deployment.

Получает: owner action, exact head, clean worktree, adapter policy.
Отдаёт: bounded lease, Access-protected URL и review evidence.
Publication и cleanup
Шесть общих slots и максимум две concurrent builds. Compose публикует изолированный stack; static — immutable bounded snapshot с fallback на корневой index для client-routed SPA paths. Ingress появляется только после health checks. Missing/mismatched SHA, dirty tree, unsafe artifact или failed health check дают fail-closed. TTL начинается после readiness; owner review не продлевает его автоматически. Cleanup всегда revoke-first.
Control plane

Discord и human control

Показывает состояние и предоставляет только актуальные допустимые действия.

Получает: Run Store state и owner component action.
Отдаёт: stable card/thread, durable request и обновлённый status.
Authorization boundary
Native plugin проверяет exact owner, guild, component ID, run identity, revision и SHA. Кнопка не выполняет shell-команду напрямую: она ставит bounded request, который повторно валидирует controller. Settings UI ephemeral и доступен только при полном idle. Telegram — только inbound fallback.
Operations

Health, guard и settings

Не даёт накопившемуся drift превратиться в скрытую поломку.

Получает: DB, Docker, disk, worktrees, tmux, backups и config.
Отдаёт: health summary, admission block, quarantine и audit.
Наблюдение без auto-delete
Runtime health read-only. Resource guard блокирует admission при опасном disk, excess worktrees или неоднозначном orphan evidence. Orphan получает 30 минут grace, затем quarantine; через 7 дней наступает owner review. Ничего не удаляется автоматически. Runtime settings имеют ranges, cross-field checks, revision guard, checksums и rollback. AI triage/day задаёт 0–40 issues на проект: 0 отключает только предложения Priority/Effort.
Recovery

Backup и Minimal DR

Позволяет восстановить решение без превращения личного проекта в enterprise-платформу.

Получает: SQLite snapshot и allowlisted non-secret config.
Отдаёт: verified local backup и encrypted S3 recovery pair.
Что входит и чего нет
Bundle содержит код из GitHub, Run Store snapshot, tracked config и scheduler inventory. Manifest и checksum проверяются до restore. Secrets, OAuth stores, Docker data и Codex sessions не архивируются. Private age key хранится только у owner-а: без него S3 bundle нельзя расшифровать.

Сквозные сценарии

Каждая строка показывает, какие подсистемы участвуют. Внутри нет отдельного скрытого workflow.

Обычная задача

Owner переводит issue в In progress; Kurami создаёт изолированную работу и собирает evidence. Только owner merge-ит PR; Done запускает проверяемый release.

Projects→Admission→Execution→CI/review→Owner merge→Done/release

Human-control задача

Run начинает CLI, затем безопасно освобождает ownership для Remote. Автономное продолжение всегда создаёт fresh successor.

Admission→Execution→Handoff→Remote→Successor

CI или review нашли проблему

Owner отдельно разрешает repair/fix; каждая техническая task ограничена snapshot и exact SHA.

Evidence→Discord action→Technical worker→New SHA→Evidence

Нужен preview

Owner запускает выбранный adapter. Completion gate принимает только healthy, exact-SHA и owner-reviewed lease.

PR head→Slot/build→Health→Ingress→Owner review

Задачу отменили

До публикации clean work можно освободить. После PR Kurami сохраняет работу и ждёт явного keep/discard решения.

Backlog→Stop writer→Revoke preview→Inspect evidence→Release / preserve

Среда выглядит подозрительно

Health/guard не пытаются «починить всё». Admission закрывается, evidence сохраняется, owner получает changed-only alert.

Observe→Block→Grace→Quarantine→Owner resolution

Границы безопасности

Если короткое правило конфликтует с удобством, Kurami выбирает доказуемость и остановку.

Один writer

Один run не может одновременно принадлежать CLI, Remote и technical worker.

Exact identity

Run, branch, worktree, PR, SHA, preview lease и Discord control связываются явно.

Owner завершает

Kurami не merge-ит PR и не deploy-ит production автономно.

Published work сохраняется

PR/remote branch не удаляются по обычной отмене; destructive cleanup требует отдельного подтверждения.

Secrets вне prompts и Git

Workers получают только необходимые bounded inputs; credential-like output отклоняется.

Не уверен — остановись

Stale state, ambiguity, drift, missing evidence и исчерпанные retries переводят работу в wait/needs attention.

Подключение нового проекта

Совместимость проверяется отдельно от запуска. Checker ничего не создаёт и не исправляет автоматически.

Минимальный контракт

  1. GitHub repository и Project v2 доступны; status field/options совпадают с registry.
  2. Canonical repo, отдельный worktree root, base branch и branch prefix заданы явно.
  3. Discord guild/project channel и общий digest channel существуют.
  4. CI либо отключён осознанно, либо required check names совпадают буквально.
  5. Triage fields заданы при включённом triage.
  6. Preview отсутствует осознанно либо полностью описывает Compose/static adapter.
  7. Два read-only polls дают baseline, затем no-op; disposable issue проходит bounded E2E и cleanup.

Полный контракт: docs/project-readiness.md.

Read-only checker

npm run readiness -- --project <key>
npm run readiness -- --project <key> --live

Config mode проверяет tracked policy. Live mode только читает GitHub и workspace.

PASS · доказано WARN · допустимо, но требует решения owner-а FAIL · admission проекта запрещён

Термины

Минимальный словарь для чтения карточек, логов и Run Store.

Run
Одна orchestration-попытка для конкретного Project item.
Admission
Атомарное решение, можно ли создать новый run и занять capacity.
Canonical checkout
Основная локальная копия репозитория; agent в ней не работает.
Worktree
Отдельная Git-копия для одного run и одной managed branch.
Writer
Текущий субъект, которому разрешено менять worktree.
Exact SHA
Конкретный commit, к которому относятся CI, review и preview evidence.
Lease
Durable право run-а на preview slot и его runtime.
Reconciliation
Повторное приведение внешних ресурсов к записанному состоянию без дублей.
Fail-closed
При недостатке доказательств действие не выполняется.
Needs attention
Автоматика остановлена; evidence сохранён для решения owner-а.
Quarantine
Не удаление, а durable отметка неоднозначного orphan resource.
Minimal DR
GitHub плюс encrypted S3 bundle и отдельный owner-held decrypt key.
