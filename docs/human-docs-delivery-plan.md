## Goal and audience

Build a complete, useful bilingual (English/Russian) human-facing documentation site for the current Kurami system at `docs.shagon1k.win`. The primary reader is the system owner/authorized operator; a new reader should grasp within a minute what Kurami is, where Digest, Project Orchestrator, and Operations fit, and what decisions still belong to the owner. Kurami is a **private agent system** / **личная агентная система**, not a synonym for the Digest dashboard or the Project Orchestrator alone. Hermes supplies the agent runtime; Kurami defines bounded workflows, deterministic guards, owner controls and durable state; Codex handles admitted engineering tasks. Avoid presenting everything as a false linear `Discord → Hermes → Kurami` pipeline: conversation/decisions and scheduled/source-driven workflows are separate entry paths. Discord is the primary owner-facing control surface; Telegram receives brief mention rather than equal prominence.

This is a text-and-diagrammatic snapshot of **verified current capabilities**, not a roadmap or an exhaustive reproduction of internal runbooks. Label trials, deployment-dependent functionality, and limits honestly. No real secrets, private mail/calendar contents, personal holdings, provider bodies, raw operational credentials, private live screenshots or exact infrastructure addresses in Git or rendered docs merely because the site is Access-gated. Do not hardcode the owner's name, a fixed schedule or timezone as a universal contract.

## Decisions from brainstorming through current implementation

- One coherent documentation site, not three separate product/operator/technical collections. Navigation has short topical nouns; each route owns one subject. Start, Understand, Digest, Projects, Operations and Changelog are the current IA; `docs/human-docs-concept.md` contains the detailed content map and three bilingual page prototypes. The homepage provides a system map and clear next routes, rather than two hero buttons implying the system is only Digest and Projects.
- A reader-facing page answers a concrete question in one or two sentences, uses a purposeful picture/comparison/steps/state legend, explains important limits, then offers **optional technical detail inline** (`details`) when it genuinely helps. Do not force the same card grid onto every page, pad a small subject to fill a template, create a mandatory separate deep-dive page, or clutter pages with repeated synthetic API disclaimers. Technical material should teach ownership, state, evidence and recovery boundaries, not invent endpoints. A tutorial/reference may use another pattern if necessary.
- RU and EN are authored and verified separately with matching route coverage (`/ru/...`, `/en/...`); no runtime machine translation. `/` and `/index.html` redirect to `/en/`, with a manual language switch. Mobile-first navigation, keyboard access, semantic HTML, readable text alternatives, light/dark theme and responsive layouts are required. Share semantic theme tokens with Digest, not its news-specific page renderer. `src/shared-ui/tokens.ts` is the shared theme foundation. No search, editor, clickable diagrams, or standalone Design Decisions pages in the agreed initial full variant.
- The visual should actually clarify the subject: accessible HTML steps, states, comparison tables, decision cards and boundary maps for simple flows. For complex spatial relationships that earn it, author an Excalidraw-style diagram: keep **editable source** in Git, export a static SVG (no production editor dependency), provide an equivalent prose explanation, verify text and arrows on mobile rather than relying on horizontal panning. Excalidraw is an option, not a mandate for every lifecycle. Do not commit real-data screenshots unless reviewed and redacted; synthetic examples are preferable. Check contrast, light/dark, reduced motion and keyboard navigation.
- Changelog must be automatic **from an externally verified successful application deploy revision**, but editorially curated: short bilingual entries grouped by date and New/Improved/Fixed/Operations, links to exact commits and optionally affected pages, no raw commit subjects promoted to public prose. A push/merge/HEAD is not deployment evidence. Unclassified commits fail the app-bound build or have narrowly justified docs-only exclusions; docs-only release with no trusted app revision has `revision: null` and an intentionally empty app changelog. Documentation and bilingual changelog entry (or explicit no-reader-visible-change classification) are part of Definition of Done for meaningful feature changes. Do not manufacture a deploy manifest. `docs/human-docs-operations.md` and `src/human-docs/changelog.ts` specify the current contract.

## Inventory and definition of completion

At handoff, the published site had **17 bilingual article routes** plus home and changelog per language (38 generated pages). This was a functioning IA and first-pass content, **not the finished editorial/visual product**. The original slugs, now defined in `src/human-docs/content/`, were:

- Projects: `project-orchestrator`, `project-admission`, `run-lifecycle`, `engineering-evidence`, `owner-controls`.
- Operations: `health`, `recovery`, `automation-boundaries`.

A route is complete only if (a) its reader question has a substantive, concise answer in both languages, (b) the right diagram/representation explains a real state or boundary with a text alternative, (c) claims are checked against implementation or the relevant internal reference and current state, (d) the current limits and safe owner actions are not hidden, (e) it passes responsive/light/dark/a11y QA and authenticated end-to-end smoke, and (f) references and navigation work. A route existing in a sitemap is not evidence of any of these.
