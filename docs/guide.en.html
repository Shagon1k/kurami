Kurami Orchestrator — system guide

Kurami turns explicit owner actions in a GitHub Project into managed engineering work. It coordinates Git, Codex, CI, previews, and Discord, preserves state across restarts, and stops whenever it cannot prove that the next action is safe.

Release: P9 · guide + readiness E2E baseline: e4ffec0 Schema: 30 Control plane: Discord Projects: TailorTales + PickFlick

System model

This is not one large bot. It is a set of independent subsystems connected by SQLite state and exact run, branch, worktree, PR, and preview identities.

01 · Intent

GitHub Project

The owner changes an issue status. This is the normal entry point for starting, cancelling, and completing work.

02 · Decision

Admission

Kurami checks the project, issue, snapshot freshness, WIP, LLM, and physical resources.

03 · Work

Isolated execution

A separate branch, worktree, and Codex task. The canonical checkout is never used as the workspace.

04 · Evidence

PR, CI, review

Every result is tied to the exact PR head SHA. Stale evidence cannot advance the lifecycle.

05 · Control

Discord + preview

The owner sees current state and can trigger only the bounded actions that are valid now.

06 · Completion

Release or preserve

Resources are released after merge. When evidence is ambiguous, work is preserved for an owner decision.

Subsystems

Read the cards in any order. The main layer explains what the subsystem is for; the expandable layer contains its internal contract and failure behavior.

Observation

Projects and priorities

Reads owner intent and explains the Backlog without starting unnecessary work.

Input: Project items, status, labels, Priority/Effort.
Output: durable events, ranked digest, metadata proposals.
Contract and resilience
The first poll creates a baseline, not runs. An unchanged repeat is a no-op. A failure in one Project blocks only new work for that project; reconciliation for existing runs continues. Metadata is written only after owner acceptance and a fresh live drift check.
Admission

Admission and limits

Decides whether a new writer can safely start now.

Input: issue event, settings, project health, resource inventory.
Output: one admitted run or an explained reject/wait.
What is checked
An open issue, correct repository/status, non-empty description, no other active run, a fresh Project poll, project/global WIP, global LLM, worktree/tmux caps, and disk thresholds. The decision and reservation share one SQLite transaction, so concurrent pollers cannot create two writers.
Execution

Git workspace and Codex

Isolates the change and guarantees one current writer.

Input: an admitted run and a fresh base branch.
Output: exact branch/worktree, managed task, and Draft PR.
Ownership and handoff
The canonical checkout stays clean. CLI, Remote, and technical workers cannot own the writer role at the same time. Takeover first brings the current task to a stable boundary. Autonomous continuation creates a new linked task instead of reclaiming the old one. Ambiguity stops the transition.
Evidence

CI and code review

Verifies the current PR revision and bounds automated fixes.

Input: exact PR/head, required check names, review threads.
Output: normalized CI, bounded findings, and a newly proven SHA.
Why exact SHA matters
An old green check does not prove a new commit. CI repair allows at most two separate owner-triggered attempts. AI review is read-only and publishes at most ten findings. Review fix uses only a snapshot of current unresolved threads, then waits for CI and resolves only that snapshot.
Preview

Compose and static preview

Gives the owner a verifiable result without a direct production deployment.

Input: owner action, exact head, clean worktree, adapter policy.
Output: bounded lease, Access-protected URL, and review evidence.
Publication and cleanup
Six shared slots and at most two concurrent builds. Compose publishes an isolated stack; static publishes an immutable bounded snapshot and falls back to its root index for client-routed SPA paths. Ingress appears only after health checks. Missing/mismatched SHA, a dirty tree, an unsafe artifact, or a failed health check fails closed. TTL starts after readiness; owner review does not extend it automatically. Cleanup is always revoke-first.
Control plane

Discord and human control

Shows current state and exposes only currently valid actions.

Input: Run Store state and an owner component action.
Output: stable card/thread, durable request, and updated status.
Authorization boundary
The native plugin verifies the exact owner, guild, component ID, run identity, revision, and SHA. A button never executes a shell command directly: it queues a bounded request that the controller validates again. The settings UI is ephemeral and available only at full idle. Telegram is an inbound fallback only.
Operations

Health, guard, and settings

Prevents accumulated drift from becoming a hidden failure.

Input: DB, Docker, disk, worktrees, tmux, backups, and config.
Output: health summary, admission block, quarantine, and audit.
Observation without auto-delete
Runtime health is read-only. The resource guard blocks admission for unsafe disk use, excess worktrees, or ambiguous orphan evidence. An orphan gets a 30-minute grace period, then quarantine; owner review becomes due after seven days. Nothing is deleted automatically. Runtime settings use ranges, cross-field checks, revision guards, checksums, and rollback. AI triage/day allows 0–40 issues per project; 0 disables only Priority/Effort proposals.
Recovery

Backup and Minimal DR

Makes the system recoverable without turning a personal project into an enterprise platform.

Input: SQLite snapshot and allowlisted non-secret config.
Output: verified local backup and encrypted S3 recovery pair.
What is and is not included
The solution is restored from GitHub plus a bundle containing the Run Store snapshot, tracked config, and scheduler inventory. Manifest and checksum are verified before restore. Secrets, OAuth stores, Docker data, and Codex sessions are not archived. The private age key stays with the owner; without it, the S3 bundle cannot be decrypted.

Cross-system use cases

Each row shows which subsystems participate. There is no separate hidden workflow behind it.

Normal engineering task

The owner moves an issue to In progress; Kurami creates isolated work and collects evidence. Only the owner merges the PR; Done starts verified release.

Projects→Admission→Execution→CI/review→Owner merge→Done/release

Human-control task

CLI starts the run and safely releases ownership to Remote. Autonomous continuation always creates a fresh successor.

Admission→Execution→Handoff→Remote→Successor

CI or review finds a problem

The owner separately authorizes repair or fix; each technical task is bounded by a snapshot and exact SHA.

Evidence→Discord action→Technical worker→New SHA→Evidence

A preview is needed

The owner starts the configured adapter. The completion gate accepts only a healthy, exact-SHA, owner-reviewed lease.

PR head→Slot/build→Health→Ingress→Owner review

The task is cancelled

Clean unpublished work can be released. After a PR exists, Kurami preserves the work and waits for an explicit keep/discard decision.

Backlog→Stop writer→Revoke preview→Inspect evidence→Release / preserve

The environment looks suspicious

Health and guard do not try to “fix everything.” Admission closes, evidence remains, and the owner receives a changed-only alert.

Observe→Block→Grace→Quarantine→Owner resolution

Safety boundaries

When a short rule conflicts with convenience, Kurami chooses provability and stops.

One writer

A run cannot belong to CLI, Remote, and a technical worker at the same time.

Exact identity

Run, branch, worktree, PR, SHA, preview lease, and Discord control are linked explicitly.

The owner completes

Kurami never merges a PR or deploys production autonomously.

Published work is preserved

A PR or remote branch is not deleted by normal cancellation; destructive cleanup needs separate confirmation.

Secrets stay out of prompts and Git

Workers receive only necessary bounded inputs; credential-like output is rejected.

When unsure, stop

Stale state, ambiguity, drift, missing evidence, and exhausted retries move work to wait or needs attention.

Onboarding a project

Compatibility is checked separately from execution. The checker never creates or fixes anything automatically.

Minimum contract

  1. The GitHub repository and Project v2 are readable; status field/options match the registry.
  2. Canonical repository, separate worktree root, base branch, and branch prefix are explicit.
  3. Discord guild/project channel and the shared digest channel exist.
  4. CI is intentionally disabled or required check names match literally.
  5. Triage fields are configured when triage is enabled.
  6. Preview is intentionally absent or fully describes a Compose/static adapter.
  7. Two read-only polls produce a baseline then a no-op; a disposable issue passes bounded E2E and cleanup.

Full contract: docs/project-readiness.md.

Read-only checker

npm run readiness -- --project <key>
npm run readiness -- --project <key> --live

Terms

The minimum vocabulary needed to read cards, logs, and the Run Store.

Run
One orchestration attempt for a specific Project item.
Admission
The atomic decision to create a run and reserve capacity.
Canonical checkout
The primary local repository copy; agents never work in it.
Worktree
A separate Git copy for one run and one managed branch.
Writer
The current actor allowed to change the worktree.
Exact SHA
The specific commit proven by CI, review, and preview evidence.
Lease
A run's durable right to a preview slot and its runtime.
Reconciliation
Repeatedly converging external resources to recorded state without duplicates.
Fail-closed
The action does not run when evidence is insufficient.
Needs attention
Automation has stopped; evidence is preserved for an owner decision.
Quarantine
A durable marker for ambiguous orphan resources, not deletion.
Minimal DR
GitHub plus an encrypted S3 bundle and a separate owner-held decryption key.
